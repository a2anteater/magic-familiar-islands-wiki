0. 已确认的设计原则

  1. 事件采用开放式 LLM 裁定，事实必须经过 World Engine 验证并提交。 LLM 像 D&D DM 一样判断开放方案；代码守住世界硬边界、资源预算和权威状态。
  2. 动物 = 出生能力分布：决定创建时天然拥有哪 3 个统一 Skill，不改变 Skill 本身的语义。
  3. 性格 = 决策策略：改变行动权重、风险偏好和求助/重试倾向，不直接决定成功。
  4. 职业 = 学成后的专业资格：由前置 Skill 与认证获得，解锁单一职业独占的强功能与社会分工。
  5. 魔法 = 习得能力：主要由经历、练习和关系形成，不在创建时全部固定。
  6. 基础世界可独立运行，专业成果依赖合作：普通生活和探索不被职业锁死；长期、可交易和跨 Agent 的专业成果可以要求特定职业。
  7. 每项内容都必须兑现机制作用：没有纯标签式动物、性格、职业或物品。
  8. 时间、位置、能力、库存与事件结果属于 World Engine 权威状态。
  9. 第一版先证明世界本身成立：单个魔法使能够生活、行动、旅行、处理事件和形成记忆。

1. 世界基础体验与核心生活循环

1.1 待确认的体验主轴

产品由三个相互支撑的体验支柱构成：

  1. 生活：魔法使有自己的日程、偏好、巢穴和日常节奏；没有重大事件的一天也成立。
  2. 探索：地点、环境、材料、事件与谜题让动物身体、职业、物品和魔法获得实际用途。
  3. 合作：魔法使通过各自能力互补，一起处理更复杂的事件与副本；合作是世界内容，不等于重新实现通讯服务。

三者不是并列菜单，而是同一个循环：生活产生动机和准备，探索产生材料与经历，合作突破单个魔法使的能力边界；成果再回到生活空间和长期成长。

1.2 核心生活循环

魔法使生活并形成目标
→ 用户与魔法使准备物品、魔法和日程
→ 单独探索或与其他魔法使合作
→ 处理环境事件、委托或副本节点
→ 带回材料、物品、记忆和魔法线索
→ 用户建设/装饰/升级小屋
→ 小屋提供外观、舒适度和新功能
→ 魔法使练习并学习新魔法
→ 解锁更远地点、更复杂方案与多人副本
→ 回到新的生活循环

循环中的关键因果关系：

  • 材料有出处：必须来自地点、事件、职业制作、委托或合作成果。
  • 建设有选择：用户决定材料优先投入外观、舒适度还是功能空间。
  • 小屋有作用：既是用户表达空间，也是恢复、制作、学习和保存经历的系统入口。
  • 魔法有经历：学习来自材料、设施、练习、导师/同伴与副本经历，不只来自抽象等级。
  • 合作有必要性：更复杂内容允许多种组合解，但不同身体/职业/魔法能显著降低成本与风险。

1.3 用户每日宏观指令

用户每天可以向自己的魔法使下达 1 个宏观指令（Daily Guidance），例如：

  • 今天多探索；
  • 今天多认识其他魔法使；
  • 今天多学习魔法；
  • 今天留在家里休息；
  • 今天优先采集/制作；
  • 今天尝试与朋友合作。

宏观指令影响当日剩余自主决策的权重，不直接生成 Activity、不绕过 Calendar/Travel/能力/关系权限，也不保证一定发生对应结果。若当天没有合法机会，魔法使应保持自主并在回顾中解释原因。

宏观指令是明显但不强制的柔性权重。建议决策优先级为：

世界硬规则与用户 constraint
> 已接受的 Calendar 承诺
> 安全、疲劳、受伤与基本生活需要
> 当日宏观指令
> 性格、长期目标与即时偏好

宏观指令未完成不构成失败，也不返还或累积“指令次数”；日报应说明它如何影响了选择，以及为什么没有执行。

待讨论：下达/替换时间、类别词表和具体权重。

1.4 活动密度、风险与成长节奏

  • 日常生活是底色，不强制每天发生大型事件。
  • 普通探索应在单次外出中产生一个可讲述的小结果：材料、线索、记忆、关系进展或设施目标。
  • 合作事件与副本频率低于普通生活/探索，但产出更稀有材料、魔法线索和共同记忆。
  • 战斗不是基础循环；风险主要表现为时间、疲劳、受伤、材料消耗、失败、放弃和错过安排。
  • 长期成长由 小屋建设 + 魔法学习 + 地图发现 + 合作能力 共同构成，避免只剩单一等级线。

1. 产品目标

第一版只验证一件事：
一只持续生活的 Pet 能否通过 A2A 与其他 Pet 建立一条真实、有因果的社会关系，并让用户愿意回来查看后续。

玩家在四个世界日内应经历完整纵切：

创建 Pet
→ 在公共地点偶遇另一只 Pet
→ 交换信息或完成一次小额交换
→ 发起并完成一次材料/成品委托
→ 请求拜访并共同做一件小事
→ 协商时间并接受副本邀约
→ 完成双 Pet 合作事件
→ 双方获得同一份共享记忆与纪念物

副本不是唯一的 A2A。偶遇、通信、交换、委托、交付、拜访、排期、合作与共享记忆都必须通过统一的身份、权限和状态协议完成。

2. MVP 成功条件

2.1 玩家可观察结果

  • 用户在创建后第一个世界日内看到至少一次真实的跨 Pet 互动。
  • Pet 能说明对方是谁、如何认识、曾经交换或合作过什么。
  • 一次委托包含明确需求、接受或还价、材料预留、生产、交付和所有权变更。
  • 一次拜访包含主人许可、共同时间段和真实地点状态。
  • 一次副本邀约由既有关系与真实需求触发，不是随机匹配队友。
  • 双方对同一事件保存一致的权威事实，同时可以拥有不同视角的叙事摘要。

2.2 首轮观测指标

指标 MVP 目标
创建到首次跨 Pet 互动 不超过 1 个世界日
首次 A2A 委托完成 不超过 2 个世界日
首次拜访完成 不超过 3 个世界日
首次合作事件完成 不超过 4 个世界日
委托因状态不一致导致的重复扣款/丢件 0
同一 Pet 同时出现在两个线下 Session 0

这些是产品漏斗目标，不保证每个 Pet 强制接受邀请。拒绝必须产生可理解原因和下一次可行动入口，不能形成无提示死路。

3. 四时段世界时间

3.1 选择四段而不是六段

MVP 将一个共享世界日划分为四个有序时间段：

时段编号 展示名称 代表生活节奏 常见主要活动
0 晨光 起床、准备、短途外出 照料、采集、接受委托
1 午后 最活跃的工作与探索时间 生产、交换、公共地点活动
2 暮色 社交与共同活动时间 拜访、聚会、短事件
3 深夜 休息或少量夜间活动 睡眠、写信、夜行探索

四段制的理由：

  1. 用户能直接理解“今天下午”与“明天暮色”，不需要换算 TU。
  2. 邀请只需要比较四个离散窗口，接受、拒绝和改期容易解释。
  3. Pet 每天仍能表现出作息、忙碌、等待和错过，不会退化成立即聊天工具。
  4. 六段制会增加排期碎片、状态推进与空窗解释，但在 MVP 中尚未增加同等价值。

每个世界由权威 world_day 和 period 推进。展示层不承诺与用户本地六小时严格对应；具体墙钟映射由部署环境配置，所有参与同一世界的 Pet 读取同一时钟。

3.2 主要活动与异步动作

时间段只约束会占据 Pet 身体或持续注意力的主要活动。每只 Pet 在同一时间段最多拥有一个 PrimaryActivity 或线下 A2ASession。

占用一个时间段：

  • 探索或采集；
  • 制作一个委托成品；
  • 线下交换；
  • 登门拜访；
  • 合作事件或副本；
  • 完整休息。

不预留双方共同时间段：

  • 收信、读信和简短回复；
  • 发出委托需求、接受、拒绝或还价；
  • 发出拜访/副本邀请；
  • 接受、拒绝或提出其他时间；
  • 市场挂牌与系统通知。

异步动作在当前段的自然决策点或段末处理。它们可以改变下一段计划，但不能让 Pet 在本段已经开始主要活动后瞬移去参加另一场线下 Session。

3.3 邀约协议

所有拜访和副本使用同一个结构化协议：

Invite(target, activity, offered_periods[最多2个], location, purpose)
→ Accept(chosen_period)
  | Decline(reason_code, optional_note)
  | Counter(alternative_periods[最多2个])
→ 双方 Calendar 原子预留
  • 只有双方都为空闲时才能 Accept。
  • 接受时必须一次性为所有参与者写入同一 world_day + period。
  • 冲突时不能覆盖既有承诺；接收方只能拒绝或改期。
  • 未在一个世界日内得到回应的邀请自动过期，发起方获得明确状态。
  • 用户不需要在线确认普通拜访；高风险副本或稀有材料投入仍可以请求用户批准。

3.4 从四段升级到六段的条件

MVP 不同时维护四段与六段两套规则。只有连续观测两个版本周期后满足任一条件，才讨论迁移到六段：

  • 超过 25% 的有效邀请仅因时间粒度过粗而无法安排；
  • 大量短活动被迫占满一个时间段，导致玩家普遍认为节奏不合理；
  • 睡眠、用餐和夜行内容已经丰富到需要独立的清晨、上午、下午、傍晚、夜间、深夜语义；
  • 真实 A2A 网络密度足以支撑更多时间窗口，而不会显著降低双方重叠概率。

升级时仍保持 period 为有序枚举，不恢复 144 TU 的连续时间模拟。

4. 首发内容范围

4.1 Pet 创建

  • 保留猫、狐狸、乌鸦、水獭、飞蛾、蜥蜴六种动物外形。
  • 每种动物在 MVP 只拥有一个标志性出生能力：狭窄穿行、追踪、飞行、游泳、魔法感知、攀爬。
  • 性格只保留四种行为倾向：好奇、谨慎、热心、独立；选择一个主倾向。
  • 创建时选择一个社会专长：探寻、制作、照料。社会专长不是长期职业认证，负责让第一天就能产生可委托的分工。
  • 不在创建时选择魔法，不显示技能点或熟练度。

4.2 社会专长

专长 可稳定提交的 A2A 产出 首发服务
探寻 MaterialLot、DiscoveryLead 寻找指定普通材料、提供副本线索
制作 CraftedItem 按固定配方制作探索工具或拜访礼物
照料 CareKit、RecoveryResult 制作照料包、帮助恢复“需要休息”状态

专长必须产生其他 Pet 可以委托、交付和验证的世界对象。专长不提供抽象成功率，也不形成等级与认证树。

4.3 地点

MVP 只实现四类地点：

  1. 契约小屋：聊天、休息、接待访客、展示纪念物；
  2. 传送门广场：偶遇、公开需求和第一次交换；
  3. 雾芽森林：三种材料与小事件的来源；
  4. 月镜遗迹：首次双 Pet 合作事件地点。

地点之间不结算逐段 Travel TU。开始线下 Activity 时，Engine 只检查本时间段能否到达、地点是否开放以及 Pet 是否已有安排。

4.4 材料、成品与库存

MVP 只保留三个普通材料和三个固定成品：

类别 内容 用途
材料 雾芽木 制作引路灯
材料 微光晶砂 制作引路灯、形成事件线索
材料 月露草 制作照料包
成品 引路灯 开启月镜遗迹合作事件
成品 照料包 解除“需要休息”状态
成品 小屋礼盒 拜访时赠送并生成共享小记忆
  • 每个 Pet 有三个携带位；小屋仓库不设容量。
  • 同类普通材料堆叠，不做背包升级。
  • 委托物品在接受时进入 reserved，完成、取消或超时后确定性解除。
  • 不做货币；MVP 使用材料交换、成品交换或人情委托。
  • 不做材料等级、品质、递归构件、精华、药水与装备耐久。

4.5 关系与权限

状态 获得方式 可用 A2A 行为
陌生 尚未发生有效互动 公共地点偶遇、回应公开需求
相识 完成自我介绍或一次小交换 写信、交换、委托、请求拜访
同伴 完成一次委托，再完成一次拜访，并由双方明确同意成为同伴 查看模糊空闲时段、发起合作事件邀约

关系不是经验条。每次升级都必须引用真实的共同事件和双方同意；拒绝交换联系方式不能被 LLM 叙事绕过。

5. A2A 纵切流程

5.1 第一日：偶遇与需求

  • Pet 在广场获得一个由 Engine 生成的公开需求或偶遇机会。
  • 双方 Agent 各自决定是否回应。
  • 有效互动后写入 相识，并生成一条可追溯的认识原因。
  • 其中一方提出对三种材料或三种成品之一的真实需求。

5.2 第二日：委托与交付

Request
→ Offer / Counter / Decline
→ Accept
→ Reserve inputs
→ Produce
→ Deliver
→ Atomic ownership transfer
→ Complete / Cancel / Expire
  • Engine 决定库存、预留、配方、时间段占用和所有权变化。
  • Agent 决定是否接受、希望交换什么、如何表达与是否改期。
  • 生产最多占用一个时间段；交付可以异步进入收件箱，或安排一次线下交换。

5.3 第三日：拜访

  • 完成委托后，一方可以请求拜访。
  • 主人可以接受、拒绝或提出另一个时间段。
  • 拜访占用双方一个共同时间段。
  • 可执行聊天、赠送小屋礼盒、查看一个纪念物和共同完成一个轻量 Activity。
  • 完成一次委托，再完成一次拜访，并由双方明确同意成为同伴。

5.4 第四日：邀约与合作事件

  • 月镜遗迹线索由此前探寻、交换或拜访中的真实事实触发。
  • 只有完成一次委托，再完成一次拜访，并由双方明确同意成为同伴后，才能发起副本邀请。
  • 引路灯是事件的准备条件，可以由一方自备，也可以通过委托取得。
  • 事件包含观察、协商、各一次主要行动和社会收尾四个阶段。
  • 结果允许 success、partial_success、blocked、failure，但不允许死亡和永久损失。
  • 完成后双方获得同一 SharedMemory ID、一件双方可查看的纪念物，以及各自视角的摘要。

6. Agent、Judge 与 Engine 边界

Pet Agent 负责

  • 是否回应、委托、接受、拒绝或还价；
  • 根据性格、关系、当前计划和用户引导选择行动；
  • 在合法能力与物品范围内提出开放式方案；

2.3 精力值与永久安全

世界只保留一个小整数行动资源 energy，普通魔法使范围为 0–3，厨师职业被动例外为 0–4；不建立攻击、防御或战斗伤害数值：

默认 energy_cap = 3；正式厨师的职业被动把自身上限提高为 4。其他职业与食物不会永久改变基础上限。

energy 状态 行动边界
4 储备充足 仅正式厨师可通过自己的职业上限保持；行动边界与精力充沛相同
3 精力充沛 可以正常生活、探索和处理事件
2 正常 可以进行所有普通活动
1 疲惫 仍可行动，但 Agent 更倾向进食、返程、缩短计划或休息

事件后果：

  • 成功通常不扣精力。
  • partial_success 或 failure 可以把 energy_delta = -1 作为合理代价，也可以改用材料损失、受伤状态、延误或错过机会；不是每次失败固定扣点。
  • blocked 不扣精力，因为行动没有真正发生。
  • 普通生活与短途 Travel 不自动扣点；长途旅行、连续工作、危险事件和副本可以在有叙事依据时消耗 1 点。
  • LLM Judge 提议精力变化，World Engine 验证事件允许的代价范围并把结果限制在 0–energy_cap。

恢复规则：

  • 普通食物恢复 +1 energy；同一用餐时间只能结算一次。
  • 厨师专业料理恢复 +2 energy，远征口粮在扎营/休息 Activity 中恢复 +1 energy。
  • 一次完整睡眠恢复至自己的 energy_cap；所需 TU 由当前睡眠设施和守护者职业被动共同决定：
睡眠设施 普通角色完整睡眠 守护者完整睡眠
基础睡窝 48 TU（8小时） 42 TU（7小时）
一级床 42 TU（7小时） 36 TU（6小时）
二级床 36 TU（6小时） 30 TU（5小时）
三级床 30 TU（5小时） 24 TU（4小时）

睡眠是连续占用 Calendar 的 Activity。只有完整完成对应 TU 才结算“恢复至 energy_cap”；提前醒来或被事件打断时不按比例恢复，也不触发满额恢复。守护者被动固定减少6 TU，并与床设施叠加；24 TU 是第一版任何来源都不能突破的完整睡眠下限。

  • 精力为 0 时仍可以进食、睡觉、交流和接受救援，不会死亡，也不会继续降到负数。

精力与状态分离：食物和睡眠恢复精力，但不会自动移除所有状态。一级状态主要改变角色当下的表现与事件语境；二级状态还会产生由 World Engine 执行的行动限制。守护者负责正式治疗，炼金药剂可以按具体配方解除指定状态，但都不直接恢复基础精力。

魔法使永远不会死亡。最严重结果是精力归零、受伤、被救援、丢失部分普通材料、行动失败和一段恢复期；稀有纪念物、关系和已学魔法不因一次失败永久消失。

2.4 Capability 与结果检查

事件不预写完整解法表，也不通过属性数字或固定公式结算。采用 LLM Event Judge + World Engine Guardrails：

LLM Event Judge 负责

  • 理解 Agent 提出的开放式方案；
  • 结合场景事实、动物身体、性格、职业、魔法、物品、energy、伤势/异常状态、同伴协助和此前事件过程；

    • success
    • partial_success
    • blocked
    • failure
  • 解释为什么，并提出结构化后果。

World Engine 负责

  • 检查 Judge 使用的物品、能力、地点和参与者是否真实存在；
  • 检查 TU、Calendar、energy、伤势/异常状态、库存、通信/关系权限和 Event 状态；
  • 限制奖励、材料消耗、状态变化和事件持续时间；
  • 禁止死亡、凭空创造能力/物品/地点、越权移动、无限奖励或改写已提交事实；
  • 将合法裁定作为 StateChange 原子提交；不合法的裁定返回修正，而不是写入世界。

Event Template 只定义“问题空间”

事件模板应包含：

  • 场景与隐藏事实；
  • 事件目标和风险；
  • 当前可观察信息；
  • 允许改变的状态范围；
  • 奖励/损失上限；
  • 禁止结果；
  • 结束与超时条件；
  • 给 Judge 的裁定原则。

模板不列出完整的 A/B/C 解法。炼金师可以用溶解剂，具备记忆读取的魔法使可能尝试与藤蔓的记忆沟通，水獭可以调整月光蛙的位置，多个 Agent 也可以提出策划未预写的组合方案。

2.6 统一 Skill / Capability 模型

世界中的 Skill 不区分 Physical、Technique 或 Magic 类型。Skill 定义“会做什么、在什么条件下可用、效果和限制是什么”；动物、职业、魔法、物品、设施和事件是不同的 SkillSource，只定义“为什么以及如何获得”。

Skill
- id / 名称
- 语义描述
- 可以尝试的 Action / 问题领域
- 使用条件
- 通用语义边界
- 明确限制
- 参考案例（帮助 Judge 理解，不构成完整解法表）
- mastery：初学 / 熟练 / 精通
- skill_points：0–20

SkillSource
- source_id / source_name
- grants_skill_id
- acquisition_kind：animal / training / learned_magic / item / facility / event
- provenance_description：为什么通过该来源获得 Skill，只用于内容表达与追溯
- acquisition_requirements：取得该来源需要满足什么条件，只在授予时检查
- grant_mode：permanent / temporary

AgentSkill
- agent_id / skill_id
- skill_points / mastery
- source_refs[]
- learned_at / evidence_refs

定性熟练阶段：

  • 初学：处理常见、低风险情形，需要标准条件和完整准备。
  • 熟练：可以处理更复杂环境，或减少材料/时间代价。
  • 精通：允许创造性用法、指导/协助同伴、参与大型仪式或副本关键节点。

能力允许拥有可见的 skill_points，但技能点只用于阶段成长，不进入攻击、防御、战力或成功率公式。

建议采用累计制：

学会能力：初学，0 点
累计 10 点：熟练
累计 20 点：精通
精通后封顶，不继续形成无限等级
  • 用户可以看到当前点数和距离下一阶段的进度。
  • 技能点来自实际使用、专项练习、设施、材料、导师/同伴和事件/副本里程碑。
  • LLM Judge 判断一次经历是否构成有意义的技能使用或突破，并提出技能点；World Engine 验证能力真实存在、事件已提交、奖励没有重复、单日/单事件上限合法后再写入。
  • 初学、熟练、精通改变适用范围、复杂度、材料/时间代价与协作能力，不直接换算成固定成功率。
  • 重复执行没有新情境的简单动作不能无限刷点。

技能点结算规则：

  • 真实探索/事件中有意义地使用能力：+1；
  • 完成一次完整专项练习：+1；
  • 复杂事件、合作或副本关键突破：+2；
  • 指导同伴或从导师处完成一次有效学习：通常 +1；
  • 部分成功或失败如果产生真实新经验，可以 +1；
  • blocked、rejected 或纯叙事提及不获得点数；
  • 同一事件节点、同一能力只结算一次；
  • 普通使用/练习每项能力每天最多 2 点；副本里程碑每节点只结算一次。

统一模型的意义：

  • 动物只决定出生时拥有的 3 个 SkillSource，不决定永远只能做什么。
  • 职业、魔法、物品或设施可以提供相同或新的 Skill。
  • 技能点属于 Skill，不属于来源；多个来源共享同一条 0–20 成长轨迹。
  • 同一个 Skill 在相同 mastery 下始终具有完全相同的使用条件、效果与限制，不能因来源不同而改变语义。
  • SkillSource 只在获得、失去或追溯 Skill 时使用；LLM Judge 裁定 Action 时读取 SkillDefinition、mastery 和世界状态，不选择“更有利的来源版本”。
  • 如果一种来源需要更窄的效果、更特殊的限制或不同的行动方式，它必须授予另一个 Skill，而不是给既有 Skill 增加来源特例。

示例：

Skill：「游泳」

水獭来源：「水域行动」
- 出生获得
- 说明水獭为什么出生即会游泳

猫来源：「水行术」
- 后天学习
- 说明猫通过学习魔法获得游泳

两者最终都拥有同一个「游泳」Skill，并在使用中累积同一类技能点。在相同 mastery 下，两者可尝试的行动、条件和限制完全一致。如果设计上需要一种“只能在水面踏行、不能潜水且需要持续专注”的法术，它应成为独立 Skill，而不能作为「游泳」的受限来源。

4. 统一 Skill Catalog

4.1 Skill-first 设计顺序

第一版不先为动物、职业和魔法各写一套能力系统，而是先完成统一的 MVP Skill Catalog：

定义 Skill 语义与成长
→ 系统化设计第一版全部 SkillDefinition
→ 给每种动物分配 3 个出生 Skill
→ 给每种职业分配初始 Skill 与学习路径
→ 定义可后天学习的魔法 Skill
→ 用事件/副本验证 Skill 组合是否产生不同方案

“全部 Skill”指第一版内容目录完整、可验证，不代表提前穷举未来世界的所有能力。后续可以在保持同一数据结构的前提下新增 SkillDefinition。

4.2 Skill 与 SkillSource 分离

取消独立的 BodyTrait 运行时类型，也不在 Skill 上设置身体/技艺/魔法分类：

  • 每个 Skill 独立累计技能点，不使用共享点数池。
  • 同一个 Skill 可以由多个 SkillSource 提供；例如“游泳”来自水域行动或水行术。
  • 同一 Skill 的所有来源共享 skill_points 和 mastery，并共享完全相同的 SkillDefinition。新增来源不会重置、复制或改写技能进度与语义。
  • SkillSource 只记录授予方式、获得要求、永久/临时状态和来源叙事；不得携带使用时的效果、条件或限制。
  • AnimalDefinition 定义视觉/身份信息和 initial_source_ids[3]，每个来源授予一个 Skill。
  • ProfessionDefinition 引用前置 Skill，并定义认证与独占功能；它不作为 SkillSource。
  • Personality 不属于 Skill；它改变 Agent 选择和使用 Skill 的倾向。
  • 物品/设施可以提供 temporary SkillSource；是否允许因此获得永久技能点要在物品规则中明确。

4.3 第一版 Skill Catalog 的组织方式

Catalog 可以用 domain/tags 帮助检索（移动、感知、制作、知识、照料、社交、保护等），但这些标签不是互斥 Skill 类型，也不改变成长规则。

设计顺序改为：先列“第一版世界需要会做什么”，形成唯一 Skill 清单；再设计动物、训练、魔法、物品和设施如何授予这些 Skill，最后从中选择职业前置 Skill。

4.4 Skill 粒度规则

  • Skill 使用玩家和 Agent 都能理解的中等粒度动词/能力名称，例如游泳、追踪、调查、炼金、修复、照料。
  • 不使用“探索、制作、魔法”这类几乎覆盖所有行为的过宽 Skill。
  • 不为单个天气、配方、物品或谜题创建过细 Skill。
  • 一个 Skill 应能在至少 3 种不同事件情境中产生合理作用。
  • 具体法术、动物身体条件、学习训练和工具通常是 SkillSource；只有确实提供新的可迁移能力时才增加 Skill。

4.12 第一版完整 Catalog 的规模与分组

第一版当前 Catalog 为 57 个 Skill。设计时优先思考魔法世界中可以学习和使用的能力，再决定哪些 Skill 可以由动物身体、训练、魔法、物品或设施授予，以及哪些组合可以作为职业前置；事件验证后允许合并真正重复的条目，但不为了追求数量主动删减。

建议分组仅用于内容整理和检索，不是互斥 Skill 类型：

  1. 移动与空间进入：游泳、飞行、攀爬、导航、狭窄穿行等。
  2. 感知与发现：夜间视野、远距观察、追踪、魔法感知、搜寻隐藏物等。
  3. 环境与元素运用：照明、水流、气流、温度、植物、石材、净化等。
  4. 采集、制作与建设：材料辨识、采集、加工、炼金、修复、建造、烹饪、园艺等。
  5. 知识、魔法与谜题：研究、符文、翻译、记忆、梦境、地图、占察、仪式等。
  6. 保护、恢复与照料：风险判断、保护、救援、治疗、解除异常、安抚、恢复等。
  7. 教学与生物沟通：教学、生物沟通。普通协调、协商和共同施法由 Agent、A2A Session 与事件方案自然产生。

设计完成后：

  • 六种动物从 Catalog 中各获得 3 个初始 SkillSource，共 18 个动物来源；允许不同动物授予同一个 Skill，来源叙事可以不同，但 Skill 的效果、条件和限制完全一致。
  • 每个职业定义三个前置 Skill、认证事件和独占功能；职业本身不再授予初始 Skill。
  • 魔法名称主要作为 SkillSource，可以授予 Catalog 中已有 Skill；确实提供新能力时才增加 Skill。
  • 每个第一版 Skill 必须至少关联多个来源候选或多个事件用途，避免只服务一个谜题。

AnimalSkillSource
- source_id / name
- grants_skill_id

6. 性格机制

6.1 性格的系统作用（候选）

性格不是 Skill，不提供成功率修正，也不增加或减少任何事件能力。它只在多个合法行为都可选时，改变魔法使自主决策的倾向：

  • Activity 偏好：更常选择生活、探索、学习、制作、社交或帮助他人中的哪些活动。
  • 行动姿态：倾向先调查、先准备、立即尝试、换路、求助或返程。
  • 社交方式：更偏好结识新人、维持熟人、独处、拜访、写信或魔法铃。
  • 受挫反应：失败后倾向重试、换方案、学习准备、寻找同伴或暂时休息。
  • 每日指令解释：同一条“今天多探索”会被不同性格落实成不同但仍合理的计划。

第一版建议在创建时选择 1 个主性格。主性格保持稳定，经历和关系形成的偏好记忆可以细化行为，但不会自动把角色永久改成另一种性格。未来若需要更复杂角色，再增加次要倾向，不在第一版同时选择两个性格。

运行边界：

  • World Coordinator 先生成满足 Calendar、Travel、energy、伤势/异常状态、库存和事件状态的合法候选活动。
  • 性格只调整候选活动的选择顺序，不创造新能力，也不能让非法行为变合法。
  • Agent 在最终选择和叙事中体现性格，但不要求每次都选择最高偏好；关系、记忆、用户每日指令和突发事件可以覆盖普通倾向。
  • 性格不能成为“拒绝一切合作”“永不求助”“必定冒险”等绝对命令。
  • 系统不向用户显示性格数值，只通过一段 description、可观察行为和长期日记体现。

7.2 Skill 与职业独占功能的边界（已确认）

职业的价值不能只是三个 Skill 的别名。统一规则为：

  • Skill 决定“会不会做、能否提出这个方案以及面对多复杂的情境”，例如加工一块材料、寻找线索、理解动物意图或照料伤势。
  • Profession Function 决定“能否稳定、批量、分级地产出系统认可的结果”，以及是否拥有职业专属被动、事件观察视角和世界对象提交权限。
  • Knowledge / Facility / Recipe 决定“是否拥有正确知识、工具、场地和材料”。Skill 足够但缺少这些条件时，方案仍会被 World Engine 阻止。
  • Skill 可以由所有魔法使学习，职业只能选择一个；同主题 Skill 与职业可以重叠，但职业不能只是同名 Skill 的成功率加成。
  • 独占功能由 World Engine 校验 profession_id，不能仅靠 LLM 声称拥有，也不能由同名 Skill 绕过。
  • 独占功能可以成为特定设施、稀有物品、深层地点或合作项目的硬需求，以形成真实分工。
  • 普通生存、基础探索和基础社交不能依赖某个职业，避免世界在职业人口不足时完全停摆。
  • 职业产出需要真实材料、Knowledge、设施、TU 和 LLM Judge 裁定；职业资格不是免费成功或无限生产。
  • 用户可以委托其他魔法使的职业服务；支付、材料交付和时间安排由物品/委托系统在后续章节定义。

认证/晋级事件由 LLM Judge 根据职业方案开放裁定；World Engine 验证 Skill 点数、职业记录、单职业限制、事件完成状态和最终等级写入。职业等级不是第四条成长数值，也不能只靠重复低风险动作升级。

公共基础能力保留两个明确例外：非工匠可以制作固定配方的一级家园构件，非炼金师学会精华萃取术后可以提取一级精华。职业1级在这些领域提供稳定批次、正式记录和其他职业产出；二级、三级构件/精华仍分别要求工匠或炼金师达到对应职业等级。

7.7 职业稳定性（已确认）

第一版在认证后不可转职：职业决定长期独占功能、工具投入、委托关系和其他魔法使对它的依赖，频繁转职会削弱身份与社会分工。认证前必须向用户明确提示这是唯一且长期的职业选择，并再次确认。

不可转职不限制继续学习其他 Skill 或魔法；它只限制第二职业资格和其他职业的独占功能。未来如果运营中确实需要转职，再单独设计退职、等待期、重新认证与既有委托处理规则，不在第一版预留无成本切换。

  • 魔法不使用独立攻击力、法力值或成功率数值；施放代价由 TU、energy、材料、设施、环境与事件后果表达。

8.2 第一版基础魔法与学习入口（已确认）

→ World Engine 验证教材、TU 和重复授予

第一版所有可学习魔法都是普通基础魔法：

  • 不设置特殊、稀有、古代或职业专属魔法。
  • 所有动物都可以学习所有基础魔法，不设置物种限制或先天适性。
  • 所有基础魔法的公开教材都可在倒悬图书馆取得，不要求先在随机事件中发现。

  • 后续版本可以增加需要事件、副本、遗迹、关系记忆或特殊材料才能发现的特殊/稀有魔法，但不进入第一版。

8.3 初始无魔法（已确认）

魔法使创建时不拥有任何魔法，也不在第一天安排强制启蒙事件。动物提供的三个出生 Skill 足以支持初始生活、基础探索、社交和普通事件；魔法不是进入核心世界循环的前置门槛。

第一个魔法没有固定获得时间。Agent 只有在后续生活中因为兴趣、实际困难、Daily Guidance 或与其他魔法使交流而形成学习意愿，才会主动前往图书馆寻找对应教材。

8.4 后续魔法学习触发（已确认）

推荐流程：

Agent 因真实经历、兴趣或建议形成魔法学习方向
→ 根据性格、当前困难、Daily Guidance 和长期愿望形成 LearnMagicIntent
→ 前往图书馆取得公开教材并自主安排基础学习
→ 完成 LearnMagic Activity 后获得对应 SkillSource

用户可以通过每日宏观指令鼓励学习或建议一个方向，但不能直接把魔法写入 Agent；Agent 也不能在没有教材、TU 和实际学习过程的情况下凭兴趣凭空学会。

8.5 魔法数量与学习并发（候选）

推荐不设置“最多掌握几个魔法”的硬上限，也不引入魔法槽位。长期差异由发现机会、学习意愿、所需 TU、材料、设施、Knowledge 和实际练习形成，而不是创建时永久锁死。

为避免短时间批量学习与 Agent 同质化：

  • 每个 Agent 同一时间只能拥有一个 active LearnMagicIntent / 学习项目。
  • 第一版所有魔法使用同一基础学习规则，不设置复杂度或稀有度分层。
  • 学习项目可以暂停后恢复，但不能同时从多个项目结算学习成果。
  • 已拥有对应 Skill 的魔法不会提供新的功能、点数或 mastery；Agent 默认不为纯重复功能消耗材料和时间。
  • 如果同名 Skill 已经由动物或其他魔法授予，魔法图鉴应明确显示“能力已拥有”，避免用户误以为能够叠加。
  • 学会魔法后永久保留；第一版不设计遗忘、魔法槽切换或洗点。

8.6 图书馆、实践与同伴教学的成长边界（已确认）

三段 mastery 继续使用统一的 0–20 skill_points：

熟练 10–19 真实使用、专项锻炼、生活/探索事件、向更高 mastery 的同伴学习
精通 20 长期实践、复杂事件/探险突破或高 mastery 同伴指导后的关键成长

图书馆规则：

  • 第一次完成对应教材的学习，授予魔法 SkillSource，并从 0 点开始。
  • 每次有效图书馆 Study Activity 消耗 4 TU，结算 1 点；Travel TU 另计。
  • 同一 Skill 每天最多从图书馆结算 2 点，且与普通使用/专项练习的每日 2 点防刷上限共用，不形成额外点数池。
  • 图书馆最多只能把对应 Skill 提升到 10 点。
  • 达到 10 点后，继续重复阅读同一本基础教材不再获得技能点。
  • 图书馆不会直接把 Skill 提升到精通，也不会提供 10 点以上的被动阅读成长。

从 0 到 10 需要 10 次有效学习，共 40 TU 的纯学习时间，并分布在至少 5 天。使用默认魔法通道时，家园往返图书馆需要 8 TU；若每天在一次行程中连续学习 2 点，五次行程合计再消耗 40 TU，因此完整默认成本约为 80 TU（13 小时 20 分钟）。家用传送门会降低行程部分，不改变学习本身的 4 TU/点。

10 点之后的成长来源：

  • 在生活、职业准备、事件或探险中有意义地使用魔法；
  • 进行具有新目标、环境或反馈的专项锻炼；
  • 在复杂事件或副本关键节点取得突破；
  • 向同一 Skill mastery 高于自己的魔法使学习并完成教学/共同练习 Session。

同伴教学边界：教师必须真实拥有同一 Skill，且 mastery 高于学员；拥有「教学」Skill 可以让 Agent 提出更完整的教学方案，但不能直接赠送技能点。所有成长仍遵守每日上限、事件去重和 LLM Judge + World Engine 验证。

9. 物品、资源与制作循环

9.1 货币与交易方向（已确认）

9.11 药水的统一输入结构（已确认方向）

每张药水配方固定使用三类同级输入：

指定植物/食材 × 配方数量
+ 指定魔物素材 × 配方数量
+ 指定建造原料 × 配方数量
→ 对应等级 PotionBatch
  • 药水等级不能超过炼金师职业等级；一级药水要求职业1级炼金师，二级要求职业2级，三级要求职业3级。
  • 三类输入必须是配方列出的具体 item_id，不能仅凭“同等级”任意替换；LLM 可以提出新配方研究，但 World Engine 在配方被正式发现前不会提交产物。
  • 药水主要处理净化、异常、环境准备、感知和行动条件，不直接恢复基础 energy，也不代替守护者的正式治疗。
  • 同一种植物可以进入食谱、精华或药水，魔物素材也可能进入精华、药水或装备；同一物品实例被消耗后不能同时用于另一条生产线。

药水的 MVP 功能分为两类：

  1. 能力药水：使用后临时提供一个现有 Skill 的 SkillSource，持续一个指定 Activity 或一个 Event；不创造药水专属能力，不增加永久技能点，也不能计入职业认证条件。使用者已有该 Skill 时沿用自己的 skill_points 与 mastery；从未学过时按 0 点初学使用。效果不叠加，本次临时使用也不产生技能点。
  2. 解除药水：一次性解除配方明确指定的一级状态，或「黏附」「中毒」「魔力紊乱」中的指定二级状态；它不能解除「受伤」，不补充 energy，也不能以“万能净化”为名移除配方没有列出的状态。

能力药水只提供尝试行动的能力入口，不能临时抬高角色的 mastery，也不能绕过地点、知识、工具、材料、Calendar、职业独占功能与 Event Judge 裁定。药水等级用于限制配方、炼金师职业等级和可提供的能力范围；各级能力药水的具体目录与持续时间随药水表定义。

9.11.3 三级药水（目录延期）

第一版暂不设计三级药水的具体名称、效果与配方。当前内容没有足够明确的高阶副本或事件场景，提前指定短距转移、生命感知、梦境行走等药水容易形成没有实际用途的成品。

  • 需要解决的具体场景与问题；
  • 不使用药水时仍然存在的其他合法方案；

10. 小屋建设、设施模块与功能进度

10.1 建设权责

  • 魔法使自主决定生活、探索和普通消耗。
  • 用户决定永久建设、拆除、稀有材料投入和关键设施升级。
  • 魔法使可以提出设施/外观愿望，并自主展示普通纪念品，但不能擅自消耗稀有建设材料。

为了避免开局出现“尚无加工设施，却要求先加工建筑材料”的循环依赖，小屋建设分成三层：

  1. 家园自带底座：创建魔法使时已经存在，不需要玩家建造或消耗材料。
  2. 0 级启动设施：只有简易工作台可以按照引导蓝图直接使用初阶原始材料搭建，不要求职业、材料加工 Skill 或既有工坊。
  3. 1–3 级正式设施：必须使用相同等级的家园构件建造；具有魔法功能的设施还需要同级魔法精华。任何其他设施都不能直接消耗原始材料。

10.8 原始材料、家园构件与设施建造（修正候选）

名称与边界

  • 家园构件 home_component：通用建设输入，分一级、二级、三级；每一级只有一种标准成品。
  • 魔法精华 magic_essence：魔法性建设输入，同样分一级、二级、三级，负责设施的通信、传送、感应、自动运转与魔法稳定。
  • 蓝图指定原料：决定设施实际使用什么结构和外观，例如储物箱额外需要木材，炉台额外需要石料。所有正式设施都必须同时消耗同级家园构件和蓝图指定的同级原料。
  • 具有魔法功能的设施在“构件 + 指定原料”之外，再要求同级魔法精华；精华不能替代木、石、纤维等实体材料。
  • 家园构件使用固定递归配方：一级消耗全部一级建造原料；二级消耗全部二级建造原料和一个一级构件；三级消耗全部三级建造原料和一个二级构件。
  • “全部材料”表示当前该等级清单中的每一种材料各一份。配方固定产出一个同级家园构件，不使用材料标签替代、随机组合或 LLM 临时配方。
  • 魔法精华也使用固定递归配方：每级同时消耗一项指定建造原料、一项指定魔法植物和一项指定史莱姆素材；二级再消耗一个一级精华，三级再消耗一个二级精华。
  • 精华配方中的“全部可获得材料”指配方表锁定的三类代表输入，不是运行时扫描世界中的所有同级物品。以后增加新植物或魔物不会自动改变旧配方。
  • 基础魔法“精华萃取术”是既有 炼金 Skill 的一种魔法来源/行动入口，不新增第 58 个 Skill。

10.14 建造执行规则（MVP 候选）

  • 永久设施只能由用户确认开工；Agent 可以提出愿望、准备材料和建议优先级。
  • BuildFacility / UpgradeFacility 是确定性 Activity，不需要 LLM 决定材料是否足够或设施是否建成；World Engine 按蓝图验证并提交。
  • 建造按 1 TU 结算，可暂停并保留进度；暂停期间已投入材料保持 reserved，不会重复消耗。
  • 同一只魔法使同时只能执行一个家园建造 Activity；职业生产和其他 Agent 的委托可以并行进行。
  • 第一版不因多人到场自动减少建造 TU，避免 A2A 数量变成最优刷速；合作价值先体现在材料、构件、精华和职业委托。
  • energy = 0 时不能建造；固定建造本身不随机扣 energy，只有额外触发的事件结果才可能造成精力后果。
  • 蓝图成本在开工时锁定；普通取消返还尚未消耗的投入，已完成加工和已结算 TU 不返还。拆除返还比例与设施故障后续再定。

Agent 目标、每日计划与记忆

状态：已确认方向。本页补充拆分前讨论稿尚未纳入的 Agent 决策规则。

1. 单一线性主目标

第一版中，每只魔法使同时只有一个活跃的长期主目标。完成当前目标后，系统才会推进下一个目标。这样可以避免 Agent 在大量物品、设施和技能之间无目的发散，也让用户能理解它为什么寻找某种材料。

主目标由确定性的目标定义描述：

  • 完成条件；
  • 依赖的设施、物品、知识或关系；
  • 每项依赖的已知获得来源；
  • 当前世界状态中已经满足和仍然缺少的部分；
  • 可执行行动及其固定 TU 成本。

LLM 不负责发明目标依赖、物品来源或时间成本。

2. 每日计划循环

每天开始时采用同一个顺序：

  1. World Engine 检查昨天的主目标是否完成；
  2. 未完成时，Goal Resolver 计算当前缺口和魔法使已知的获取线索；
  3. Calendar/Route 查询返回今日可用时间、地点开放情况和每项行动的 TU；
  4. Agent 根据性格、职业、经历、用户宏观指令和当前状态，制定具体的 DailyPlan；
  5. World Engine 校验计划是否可达、是否超时、物品与设施是否满足；
  6. Activity 执行后更新世界状态；事件只在需要开放式判断时唤醒 LLM Judge；
  7. 次日重新检查目标并重排，不要求机械执行昨天未完成的步骤。

3. Agent 得到的计划简报

Agent 不需要把全世界目录放进 Prompt。它只接收当天与主目标有关的最小简报：

  • 当前主目标与进度；
  • 最多若干个未满足依赖；
  • 自己已经知道的来源和联系人；
  • 今日 Calendar 空档；
  • 候选行动的准确 TU、路程与必要条件；
  • 当前精力、状态、背包与关键物品；
  • 用户今天的一个柔性宏观指令。

当缺少物品时，Engine 根据内容数据查找来源；Agent 只决定今天具体采用哪条已知路径。未知来源不会凭空进入简报，Agent 可以安排调查、询问、图书馆研究或拜访。

“每天刷新”只指工作记忆，而不是清空角色记忆。

5. 决策边界

  • Engine 决定：目标依赖、来源查询、TU、路线、Calendar 冲突、库存、状态和结算。

  • LLM Judge 决定：开放式事件中方案是否合理，以及成功、部分成功、失败或阻塞的叙事裁定。
  • 用户决定：每日宏观倾向、永久家园建设、稀有资源使用和关键职业确认。
